<p>拿到一条住宅出口，很多人第一件事就是直接登号，结果一上来就撞验证码，然后开始怀疑线路。其实这类问题九成出在没分层：账号、网络、环境、任务四层是叠起来的，下面一层没摆正，上面那层怎么调都不对。这篇按分层拆解的路子写，从领试用号开始，一层一层往上，每层给出具体的检查项和通过标准，最后再谈放量的节奏。</p>

<h2>一、第一层：试用号到手，先别急着登正式号</h2>
<p>试用期的价值就在于可以随便试错。建议专门准备一个不重要的号用来验证环境，别拿主力号去趟雷。拿到试用号后先做三件事：确认能连接、确认出口 IP 与承诺一致、确认目标站点能打开。三件都过，再谈下一步。</p>
<h3>连接测试怎么做</h3>
<p>不看面板上写的在线状态，自己发请求。最简单的方式是请求一个显示出口 IP 的接口，连发五次，看五次返回是否同一个。如果五分钟内就变了两三次，这条线不是静态的，后面做固定出口的方案要重新考虑。</p>
<h3>目标站点先手点一遍</h3>
<p>用干净浏览器手动打开你要用的站点，别一上来就跑脚本。看三件事：页面能不能正常加载、有没有直接弹验证、语言和地区显示是否合理。手动这一遍能排除掉大部分线路问题。</p>

<h2>二、第二层：网络层，出口、DNS、时区三处对齐</h2>
<p>这一层最容易被略过，但它是后面所有问题的源头。出口对了，DNS 还在本地解析，时区还是原来那个，等于三个信号互相打架。</p>

<h2>三、第三层：环境层，客户端这些细节要对上</h2>
<h3>时区、语言、字体三件套</h3>
<p>时区要和出口城市一致，语言要和当地常用语言一致，字体列表不要出现明显不属于该地区的组合。这三样不需要多高深，只要别自相矛盾。有次排查一个反复触发验证的号，最后发现是时区改了但语言没改，两个字段打架。</p>
<h3>别在同一台机器上反复切换</h3>
<p>同一台机器上，一个环境用完就清干净再开下一个，别在两个号之间来回切。切换留下的缓存、Cookie、本地存储，都可能成为关联线索。如果条件允许，一号一台虚拟机或一个独立浏览器配置，这是最省心的做法。</p>

<h2>四、第四层：任务层，小批量跑通再谈别的</h2>
<p>环境都对齐了，开始跑真实任务，但量要小。我的习惯是先跑二十次请求，间隔拉到两秒以上，观察失败率和验证页出现次数。二十次里失败超过两次，或者出现一次验证页，就停下来查，不要继续加量。</p>
<p>这一步还要验证一件事：长会话会不会断。跑一个持续十分钟的会话，看中途有没有掉线。住宅线路绕路多，长连接偶发中断是正常的，但如果十分钟断三次，这条线的质量就不适合长会话任务。</p>

<h2>常见问答</h2>
<h3>试用号能直接用来跑正式任务吗？</h3>
<p>答：不建议。试用线路通常和正式线路不是同一批，落点也可能不同。试用期只用来验证流程通不通，正式放量前要在正式线路上再走一遍小批量。</p>
<h3>落地页没有验证码，是不是就可以放量了？</h3>
<p>答：还差一步。没有验证码只说明当前这一次访问干净，还要看连续访问的稳定性。建议至少跑二十次请求、间隔两秒以上，确认失败率低、没有验证页反复出现，再进入小批量。</p>
<h3>DNS 一定要走出口侧吗？</h3>
<p>答：多数情况下建议走。解析结果和出口地区一致，页面加载的地区化内容才不会错位。个别场景需要本地解析，那就接受这个小不一致，但要知道它是已知变量，出问题时别忽略。</p>
<h3>放量到多少算满载？</h3>
<p>答：看线路实际上行带宽，不看服务商标称的并发数。实测单条线上行常在 10 到 50 Mbps，按每个并发占用一两兆估算，再打七折留余量。超了就会开始丢包，表现是延迟忽高忽低。</p>
